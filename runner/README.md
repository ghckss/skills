# Runner

`runner`는 복잡한 소프트웨어 변경을 요구사항 계약부터 구현, 검증, 리뷰, 커밋까지 단계적으로 운영하는 Codex 스킬입니다. 구현 전에 범위와 계획을 두 번 승인받고, 승인 이후에는 정해진 범위 안에서 작은 단위로 구현을 이어가는 워크플로를 제공합니다.

## 언제 사용하나요?

다음과 같은 작업에 적합합니다.

- 요구사항과 비기능 조건을 먼저 합의해야 하는 기능 개발
- 여러 파일이나 시스템 경계를 건드리는 복잡한 리팩터링
- 구현과 함께 구조 검토, 회귀 검증, 데드 코드 정리가 필요한 작업
- 역할별 검토나 리뷰 스웜을 포함한 통제된 에이전트 워크플로
- 각 구현 단위를 검증하고 별도 커밋으로 남겨야 하는 작업

작은 문구 수정이나 단일 파일의 명확한 변경처럼 승인 게이트의 비용이 더 큰 작업에는 일반적인 구현 흐름이 더 적합합니다.

## 실행 흐름

```text
요청
  → 요구사항 계약 작성
  → Gate 1: 요구사항 승인
  → 구현 계획 작성
  → Gate 2: 계획 승인
  → 구현 자동 진행
  → 단위별 검증과 리뷰
  → 단위별 커밋
  → 최종 검증
  → 범위 내 개선점 확인
```

### Gate 1: 요구사항 계약 승인

코드를 수정하기 전에 다음 내용을 계약 형태로 정리합니다.

- 목표와 비목표
- 제약 조건
- 인수 기준
- 경계 사례
- 미해결 질문

사용자의 명시적인 승인 전에는 구현 계획을 세우거나 코드를 변경하지 않습니다.

### Gate 2: 구현 계획 승인

승인된 요구사항을 기준으로 저장소를 조사한 뒤 다음 내용을 제시합니다.

- 구현 단계와 작업 분할
- 변경할 가능성이 있는 파일
- 아키텍처 영향과 위험
- 배포 또는 전환 시 고려 사항
- 검증 전략
- 청크별 커밋 경계
- 구조 건전성 및 데드 코드 정리 계획

이 계획도 사용자의 명시적인 승인을 받은 후에만 구현을 시작합니다.

### 구현 자동 진행

Gate 2 승인 이후에는 승인된 범위 안에서 다음 작업을 추가 승인 없이 진행합니다.

- 작은 청크 단위 구현
- 린트, 타입 검사, 테스트, 빌드, 런타임 검증
- 실패 시 제한된 자동 수정
- 독립적인 영역별 리뷰와 결과 병합
- 안전하고 범위 내인 리뷰 수정
- 승인된 계약 안에서의 계획 보정
- 검증을 통과한 청크의 커밋

삭제, 강제 푸시, 배포, 비밀 정보 처리, 범위 확장처럼 위험하거나 계약을 바꾸는 작업은 Gate 3에서 다시 승인을 요청합니다.

## 역할과 상태 관리

Runner는 작업을 다음 역할로 분리합니다.

| 역할 | 책임 |
| --- | --- |
| Spec Agent | 요청을 요구사항 계약으로 정리 |
| Tech Lead Agent | 저장소를 분석하고 구현 계획과 위험을 설계 |
| Executor Agent | 승인된 계획을 작은 청크로 구현하고 검증 |
| Reviewer Swarm | 정확성, 보안, 타입, 성능, 접근성, 테스트, 유지보수성을 독립 검토 |
| Merge Reviewer | 중복과 근거 없는 지적을 제거하고 조치 항목을 통합 |
| Final Validation Agent | 최종 결과를 계약과 인수 기준에 대조 |

실제 서브에이전트는 사용자가 위임, 병렬 작업, 리뷰 스웜을 명시적으로 요청하고 도구가 지원할 때만 사용합니다. 그렇지 않으면 동일한 역할을 분리된 순차 검토로 수행합니다.

작업의 공용 기억은 대화 전체가 아니라 간결한 State Store로 관리합니다. 여기에는 요구사항, 구현 계획, 결정 기록, 검증 로그, 리뷰 보고서, 현재 코드 상태, 청크 커밋 기록, 남은 이슈가 포함됩니다.

## 검증과 복구

- 구현 후 저장소에 맞는 린트, 타입 검사, 테스트, 빌드, 런타임 검증을 수행합니다.
- 자체 검증 실패 시 자동 수정은 최대 2회 수행합니다.
- 리뷰 수정과 재검토도 최대 2회로 제한합니다.
- 저장소 현실이 계획과 다르면 무리하게 구현하지 않고 Plan Patch를 작성합니다.
- P0/P1 문제는 해결해야 하며, 해결되지 않으면 차단 사유를 보고합니다.
- 현재 변경으로 불필요해진 코드만 제거하고, 관련 없는 정리 아이디어는 후속 후보로 기록합니다.

## 커밋 정책

기본적으로 검증과 리뷰를 통과한 각 구현 청크를 별도 커밋으로 남깁니다.

- 현재 청크에서 의도적으로 바꾼 파일만 스테이징합니다.
- 사용자에게 이미 있던 관련 없는 변경은 포함하지 않습니다.
- 실패하거나 검증하지 못한 청크는 커밋하지 않습니다.
- 기본 동작으로 원격 저장소에 푸시하지 않습니다.
- 사용자가 청크별 커밋을 원하지 않으면 해당 작업에 한해 재정의할 수 있습니다.

## 완료 후 개선

최종 검증 뒤 승인된 요구사항과 계획 범위 안에 명확한 결함이 남아 있으면 최대 2회의 Refinement Loop로 보완할 수 있습니다. 새로운 기능, 공개 API 변경, 아키텍처 변경처럼 기존 범위를 벗어나는 개선은 자동으로 수행하지 않고 Gate 3에서 사용자에게 알립니다.

## 사용 예시

```text
$runner로 사용자 알림 설정 기능을 구현해 줘. 요구사항 계약부터 시작하고 각 청크를 커밋해 줘.
```

```text
$runner를 사용해 결제 처리 모듈을 리팩터링해 줘. 보안과 회귀 테스트 리뷰 스웜도 포함해 줘.
```

초기 응답에서는 바로 구현하지 않고 요구사항 계약을 제시한 뒤 승인을 기다립니다. 승인 표현의 예시는 `승인`, `진행해`, `approve`, `go ahead`입니다.

## 최종 보고

완료 시 다음 내용을 간결하게 보고합니다.

- 최종 변경 사항
- 실행한 검증과 결과
- 청크별 커밋 기록
- 남아 있는 알려진 문제와 후속 후보
- 리뷰 요약과 잔여 위험

## 파일 구성

```text
runner/
├── README.md
├── SKILL.md
└── agents/
    └── openai.yaml
```

- [`SKILL.md`](./SKILL.md): 승인 게이트, 역할, 반복 제한, 검증 및 커밋 정책의 전체 동작 계약
- [`agents/openai.yaml`](./agents/openai.yaml): 표시 이름, 설명, 기본 호출 프롬프트

README는 사용자용 설명입니다. 실제 실행 규칙을 변경할 때는 `SKILL.md`를 기준으로 수정하고 README와 UI 메타데이터도 함께 일치시켜야 합니다.
